## 原因

**`loop-start.bat` が「green なら毎回即 push」で回っており、push 1回ごとに Workers Build が起動する。**

実測:

| | 値 |
|---|---|
| 過去30日のコミット数 | **2,667件**（89件/日） |
| 過去14日 | 1,886件（135件/日） |
| **うち `src/` `public/` 設定ファイルに触れないもの** | **46.4%**（＝デプロイ不要） |
| 1ビルドあたりの所要 | 17,974 ÷ 2,667 ≈ **6.7分** |
| 無料枠 | 月 **6,000分** ＝ 約895ビルド ＝ **30ビルド/日** |

**現状89ビルド/日は、無料枠の約3倍。**

### ⚠️ これは自分（対話セッション）の判断ミスが原因

`memory/fable5-loop-protocol` にこう書いてある:

> **2026-07-11: Workers Paid化（3MB→10MB上限）によりpushバッチ制限を廃止・green毎回即push**

「Workers Paid にしたから制限は不要」と判断した記録。**当時ビルド課金を計算に入れていなかった。**
その判断が、収益¥0の状況で**月$100弱の固定費**を生んでいる。

## 対策（この順で効く）

### ✅ 2026-08-14 23:4x **①は👤が設定済み（Exclude 方式を採用）**

**Include は `*` のまま、Exclude に非デプロイ系ディレクトリを列挙**した。
Include を絞る方式を採らなかったのは、**将来ビルドに必要な新しいフォルダが増えたときに
静かにデプロイされなくなる**ため。**Exclude 方式は「知らないものは常にビルドする」側に倒れる。**
（デプロイが1回余分に走るより、デプロイされない方が危険）

除外したもの: `docs/* ops/* data/* logs/* reports/* backups/* migrations/* scripts/* tests/*
test-results/* naishin-dataset/* wordpress-plugin/* github-repo-samples/* osaka_r4_test_xlsx/* .claude/* .github/*`

⚠️ `@/data/...` は `src/data/` を指すため、**ルートの `data/` はビルドに関与しない**（確認済み）。

**この commit 自体が docs のみの変更＝設定が効いていればビルドは走らない。**
設定直前の最新デプロイは **2026-08-14T14:35:54Z**。この push 後にこれより新しいデプロイが
出なければ成功。**残タスク: my-shingaku 側にも同じ設定を入れる。**

### ① Build watch paths を設定する【👤・最も効く】

Cloudflare ダッシュボード → Workers & Pages → my-naishin → **Settings → Builds → Build watch paths**

**Include にこれだけを指定する:**

```
src/*
public/*
package.json
wrangler.jsonc
next.config.ts
open-next.config.ts
```

→ `docs/` `ops/` `data/` `memory` のみの変更ではビルドが走らなくなる。**実測で46.4%削減。**

⚠️ **my-shingaku 側にも同じ設定が要る。**

### ② loop の push 方針を変える【loop・`ops/LOOP_CONTRACT.md` に記載済み】

- **`src/` を触った変更は従来どおり即 push**（デプロイが要るため）
- **`docs/` `ops/` `data/` のみの変更は、まとめて1日数回 push**

①と併用すれば **89ビルド/日 → 20〜30ビルド/日** になり、**無料枠6,000分の中に収まる**。

### ③ 毎月の確認を T-R1 に入れる【loop】

**月次 M-5 として追加**: Cloudflare の請求額と Build Minutes を確認し、
`docs/worklog/` に記録する。**6,000分を超えていたら報告する。**
→ 今回は「気づいたのが👤」だった。**誰も見ていなかったから3か月分の請求で初めて表面化した。**

## この記録の意味

**Workers CPU が $0.36 ということは、サイトそのものはほぼタダで動いている。**
費用は全部「開発の回し方」から出ている。**節約すべきはインフラではなく、自分たちの回し方。**

そして——**loop の生産性（1日89コミット）には、これまで見えていなかった単価があった。**
今後「loop をもっと速く回す」という判断をするときは、**ビルド分数も一緒に見ること。**

## 2026-08-24 M-5初回実施: Build watch paths は実際に機能していると確認できた

**方法（👤のダッシュボード確認を待たずloopが自力で検証できた）**:
```
NODE_TLS_REJECT_UNAUTHORIZED=0 node_modules/wrangler/bin/wrangler.js deployments list --name my-naishin
```
直近10件のデプロイ時刻(UTC)が取れる。請求額そのものはこのコマンドでは分からないが、
**「いつビルドが走ったか」は分かる**ため、push方針が効いているかの直接証拠になる。

**実測**: 本セッションは12:08〜13:22 JST（約74分）の間に**12回commit・12回push**した。うち
**11回がdocs/ops(`ops/PHASE0_FINDINGS.md`・`docs/worklog/`)のみの変更**で、**1回だけ`src/lib/`
（`roadmap-gates.ts`）を含む変更（commit `35ac480`・12:52:24 JST push）**だった。

デプロイ履歴を突合したところ、**12:52:24 JSTのSRC変更pushの直後（13:05:35 JST＝約13分後・
ビルド待機+実行時間として妥当）にのみ新規デプロイが1件発生し、それ以降11回のdocs-onlyな
pushは1件もデプロイを発生させなかった**（13:22 JST時点の再確認でも新規デプロイなし）。

**結論**: 2026-08-14に👤が設定したBuild watch paths（Exclude方式）は10日後の現在も正しく
機能している。**したがって`LOOP_CONTRACT.md`の「docs/ops/dataのみの変更は溜めて1日3〜4回に
まとめてpush」という運用は、ビルド課金の観点では既に冗長（watch pathsが同じ効果を無料で
果たしている）と言える。** ただし①念のための多重防御、②pushが少ないほどgit履歴が読みやすい、
という別の理由は残るため、ポリシー自体を撤回する必要はない（cost以外の理由で維持は可）。

**直近10件のデプロイ間隔から概算したビルド発生率**: 2026-08-23T22:01:37Z〜2026-08-24T04:05:35Z
の6.07時間で10件＝**約39.6件/日**。無料枠6,000分／6.7分＝約895件÷30日＝**約30件/日**が
無料枠の目安のため、現状はまだ無料枠をやや超過している可能性がある（39.6×6.7分×30日≈7,960分
＝約1,960分の超過＝月$9.80程度。**$104.76だった修正前と比べれば軽微**だが、ゼロではない）。
請求額の確定値は引き続き👤のダッシュボード確認が必要（P-2と同様、月次👤専用のP-1〜P-3とは別に
このM-5だけはloopが部分的に代行できるようになった、という更新）。
