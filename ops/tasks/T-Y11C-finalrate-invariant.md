## きっかけ

2026-09-02 22:07、miyagi のパーサが **既存データ側の計算バグ**を発見した。
`finalRate` 7件が四捨五入の境界値（204÷160=1.275 等）で、JS の `Number(x.toFixed(2))` が
浮動小数点の都合で **切り下げていた**（1.28 が 1.27 になっていた）。

**これは「miyagi の1県の問題」ではない。同じ実装で全県の finalRate が作られていれば、
同じ条件のレコードすべてに同じことが起きている。**

## 対話セッションの実測（loop はこれを再現してから進むこと）

47県の `src/data/competition-rates/*.ts` を**テキストとして**読み、
`quota` / `finalApplicants` / `finalRate` の3つ組を正規表現で抜き、
**整数演算だけで**（JS の浮動小数点を一切通さず）検算した。

```
検算できたレコード       21,875 件
四捨五入の境界値(x.xx5)   3,181 件 (14.5%)  ← バグが顕在化しうる母数
単純な四捨五入と食い違う  1,037 件 (4.74%)
```

食い違い 1,037 件の内訳（「データが正しい説明」を先に試した結果）:

| # | 説明 | 件数 | 判定 |
|---|---|---|---|
| ① | 県が**小数第1位**で公表している | 835 | データは正しい（yamaguchi 446 / nagasaki 378 が大半） |
| ② | 県が**切り捨て**で公表している **or** toFixed の丸めバグ | 175 | ⚠️**この2つは算術だけでは区別できない** |
| ③ | **どの説明にも当てはまらない** | 27 | ★要調査 |

### ⚠️ ②が最重要の論点

**切り捨て公表と、JS の浮動小数点バグは、境界値では同じ値を出す。**
だから「stored が切り捨てと一致する」ことは、データが正しい証拠にならない。

miyagi では **PDF を実際に読んだから**「PDFは1.28と印字している＝バグ」と確定できた。
残り 170 件は PDF を読むまで確定できない。**推測で書き換えないこと。**

### ③原因不明の27件（全件）

```
yamanashi 20件  ← 193件中20件（10%）。ここが最大
yamaguchi  5件
aichi      1件   744/300 = 2.4800 だが 2.49 が入っている
hokkaido   1件   163/200 = 0.8150 だが 0.815 が入っている（小数3桁＝明らかな異物）
```

**yamanashi の20件には規則性がある。** stored が一貫して計算値より小さい:

```
 80/ 80 = 1.0000  → 保存 0.99
 55/ 55 = 1.0000  → 保存 0.98
118/108 = 1.0926  → 保存 1.08
 11/ 21 = 0.5238  → 保存 0.48
 17/ 16 = 1.0625  → 保存 1
```

`quota × stored` を逆算すると **finalApplicants より1〜2小さい値**になる。
→ 仮説: **finalRate と finalApplicants が別の時点のスナップショット**
（倍率は志願変更前、志願者数は志願変更後、等）。
⚠️ **仮説のまま扱うこと。PDF で確かめるまで書き換えない。**

## なぜパーサ1県より先か

1. **範囲が違う。** パーサ1県 = 1県ぶんの自動化。この検証 = **47県21,875件すべての健全性**
2. **9/6 に外へ出る。** 提案書の第5章は「正確性をどう担保しているか」で 226行削除を挙げている。
   **買い手が最初にやる検算は `applicants ÷ quota` と `finalRate` の突合**。
   4.74%が合わないことを、こちらが先に説明できる状態にしておく必要がある
3. **これから作るパーサが全部楽になる。** 不変条件があれば、新しい県のパーサ出力を
   「県の公表流儀に合っているか」で自動判定できる
4. **fail-closed が効いた前科がある。** 2026-09-02 00:08、kagawa を台帳に足したとき
   `PUBLIC_LICENSE_SUMMARY` の5テストが落ちて漏れを検知した。同じ形をここにも作る
