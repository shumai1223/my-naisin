# T-C5: ヒアリング希望項目リスト（★最優先・小さいが時限性が最も高い）

## 先方の言葉

> 「もしよろしければ、**ヒアリングの希望項目をご共有ください。検討の叩き台にできればと思います。**」
> 「こちらは相手のある話ではありますので、**何か別の企画等とあわせて**、進め方を検討するのがよさそうです」

## なぜ最優先か

- **先方が具体的に要求している**（提案書より先に応えられる）
- **小さい**（提案書は時間がかかるが、これは数日で出せる）
- **返ってくる答えが提案書の材料そのものになる**（順序として正しい）
- 「別の企画と合わせて」＝ 先方の追加コストが小さい ＝ **実現可能性が高い**

## 作るもの

`ops/tasks/T-C5-hearing-items.md` に、**先生に聞く8〜12問**を用意する。

**設計原則:**
- **先方が既存の調査に相乗りしやすい形**にする（独立した長大なアンケートにしない）
- **答えが仕様に直結する問い**だけを残す（「関心がありますか」型の聞くだけ無駄な問いを入れない）
- 1問ごとに「**この答えが何を決めるのか**」を添える（先方が価値を判断できる）

**必ず入れる観点:**

| # | 聞くこと | 何が決まるか |
|---|---|---|
| 1 | 生徒の学習成績の状況（評定平均）を算出する場面はあるか。年に何回か | 需要の実在と頻度 |
| 2 | 現在どうやって算出しているか（手計算／Excel／校務システム／業者） | **競合と代替手段** |
| 3 | 1人あたり・1クラスあたりどれくらい時間がかかるか | **削減価値の定量化** |
| 4 | **対象科目の範囲（どの学年・どの科目まで）はどう扱っているか** | **T-C4の大学版の仕様が決まる** |
| 5 | 教科ごとの学習成績の状況を出す場面はあるか（「英語4.0以上」型の基準への対応） | T-C4 ②の要否 |
| 6 | 校内選考の資料はどう作るか。誰が作るか | 誰向けの画面か |
| 7 | 生徒本人に「あと何が必要か」を示す場面はあるか | T-C4 ③⑤の要否 |
| 8 | 生徒の成績データを外部サービスに入れることへの抵抗はどの程度か | **§T-C8の設計要件** |
| 9 | 学校が導入する場合、誰が決めるのか | 決裁ルート |
| 10 | いま進路指導で一番時間を取られている作業は何か | 次の商品 |

⚠️ **PIIを聞かない。** 学校名・生徒名・具体的な成績は項目に入れない。

## DoD
- [ ] 8〜12問が1ファイルに収まっている
- [ ] 各問に「この答えが何を決めるか」が添えられている
- [ ] PIIを聞く項目が1つも無い
- [ ] **メール下書きまで作る**（送信は👤）

# T-C6: 過去問 × 総合得点の接続（★社内拡大のトリガー）

## 先方の言葉

> 「『**高校入試問題正解**』っていうですね、ご存知ですか。毎年出してるんですけれども、
> そういったコンテンツも結構、今回頂いたお話で**親和性があるんじゃないか**なと」
> 「『高校入試問題正解』『**大学入試問題正解**』といった過去問コンテンツが、
> **もし次回ご提案いただく内容に関連するようでしたら、改めて関係各署にも声をかけたい**と思います」

## なぜ重いのか

**これは条件付きの約束である。** 条件は「**提案内容が過去問コンテンツに関連していること**」。
つまり **ここを実装で示せるかどうかが、社内が広がるかどうかを決める。**

## 何を作るか

**「過去問を解いた」から「合格圏か」までの橋を架ける。**

現状: `/total-score` は47都道府県の総合得点方式を持っている（13県は計算機・34県は解説）。
しかし **「過去問の自己採点結果から入る」導線が無い。**

- 過去問を解いた5教科の点数を入力
- 自分の内申点（既存の `/naishin` の資産）と合算
- **その都道府県の方式で総合得点を出す**
- 「この点数は何を意味するか」を示す

**なぜ他に無いか**: 過去問は解ける。点数も出る。**でもその点数で受かるかは、内申と合算しないと分からない。**
47都道府県で合算方式が全く違うため、**過去問の出版社側では答えられない。** ここに橋が架かっていない。

⚠️ **合否判定・ボーダーラインは出さない**（Y-0憲法・永久禁止）。出すのは**総合得点という公表方式に基づく数値まで**。

## 実装
- `/kakomon-jisaiten`（仮）— 過去問自己採点 → 総合得点への橋渡し
- 既存の `/total-score/[code]` と `/naishin/[code]` を繋ぐ
- 大学側（大学入試問題正解）はT-C4の学習成績の状況と繋ぐ

## DoD
- [ ] 過去問の点数入力から総合得点までが1つの導線で繋がる
- [ ] 47都道府県すべてで、少なくとも「その県の方式の説明」に着地する
- [ ] 合否判定・ボーダーの推定を1つも出していないことをgrepで確認
- [ ] 提案書に「このURLを見てください」と書ける状態

# T-C7: 埋め込みウィジェットの試作（★提案書にデモURLを書ける）

## 先方の言葉

> 「個別に展開していくというよりは、**我々のような企業が元々あるサービスを使って提供するサービスの
> 機能の一つとして組み込んではどうか**というようなご提案ですかね」（先方が自分で言語化した）
> 「**具体的にどういった形でこのツールを連携して**実際に学校の方に提供していくのが、
> シュウマイさんとしてはこう希望されているところですかね」

## なぜ重いのか

**先方は「組み込む」という言葉を自分から使った。** しかし**組み込んだ姿を見ていない。**
提案書で「APIがあります」と書くのと、「**このURLを開いてください。御社のサイトに貼ったらこう見えます**」
と書くのでは、届き方が違う。

## 作るもの

**1行貼れば動く埋め込みウィジェット。**

```html
<script src="https://my-naishin.com/embed/gakushu-seiseki.js"></script>
```
または `<iframe src="https://my-naishin.com/embed/...">`

- **学習成績の状況の計算**（T-C4のエンジンを使う）
- ホスト側のデザインに馴染む最小限のUI
- **クレジット表記「データ提供: My Naishin」を必須にする**（非金銭4点セットの実装）
- **デモページ**を作る: 「パスナビ for School に貼ったらこう見える」という想定のモック
  ⚠️ **先方のロゴ・実際の画面を複製しない**（模倣と受け取られる）。あくまで汎用の「先生向けサイト」のモックにする

## 既存資産
バックログの X-25 / X-28（埋め込みウィジェット製品化）が該当。**そこを引き継ぐ。**

## DoD
- [ ] 1行のscriptタグで動く
- [ ] クレジット表記が外せない実装になっている
- [ ] デモページがあり、提案書からリンクできる
- [ ] 先方の商標・画面を複製していない
- [ ] 埋め込み先のドメインを制限できる（キー発行と紐付け）

# T-C8: 「生徒の成績を受け取らない」設計を実装で証明する

> 「先生方にとって『生徒の評価』というのは、**大変デリケートな領域**で、
> ご存知の通り、**センシティブな扱いが求められる情報**でもあります。
> **外部の事業者が踏み込む領域としては、高次元のトピック**ということもあり、
> まだ表立って展開されている関連サービスが少ない」

## これは説明ではなく警告である

**社内検討で必ず出る反対意見を、先方が先に教えてくれている。**
言葉で「安全です」と書いても通らない。**構造で証明する。**

## 作るもの

1. **APIのリクエストスキーマそのものを証拠にする**
   - 氏名・学籍番号・学校名・生年月日を**受け取るフィールドが存在しない**
   - 存在しないので送れない。「送らない運用」ではなく「**送れない設計**」
2. **保存しないことの明示**（計算して返すだけ・ログにリクエストボディを残さない）
3. **`/developers` と `/reliability` に専用セクション**を作る
   - リクエスト例・レスポンス例を並べて「ここに個人が特定できる情報が1つも無い」ことを見せる
4. **`ops/` に「学校・企業向けデータ取扱い方針」1枚**を作る（提案書に添付できる形）
5. **埋め込みウィジェット（T-C7）も同じ保証**にする（ホスト側から個人情報が飛ばない）
